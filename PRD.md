# Sales Guru — Product Requirements Document

## 1. Summary

Sales Guru is an AI-powered advertising platform for small-to-medium businesses: a user links their business, describes what they sell, and the platform generates ad strategy, ad copy, and ad creative using AI — then publishes real campaigns to Meta Ads and reports back on results.

Functional reference for scope/pricing: saleads.ai/es/subscribe. Sales Guru is an independent product — own name, brand, and copy, not a reskin.

**Vertical scope (confirmed 2026-08-31):** MVP is scoped to the jewelry & accessories industry only, not general-purpose across industries. The Marketing Strategist Agent (§5 step 5) is grounded with jewelry-specific knowledge and validated industry benchmarks for this vertical rather than staying industry-agnostic.

## 2. MVP core loop

The MVP is this end-to-end flow, in order. Each step is a fully working component before moving to the next (see §5, Build order).

**Objective-first (confirmed 2026-09-04):** selecting a campaign's objective is the *first* thing a user does after creating a business, ahead of describing a product or defining an audience — an objective (SALES/LEADS/TRAFFIC/MESSAGES/AWARENESS) needs no product/audience in view to be meaningful, and this matches Meta Ads Manager's own objective-first flow, reducing the gap between this app's mental model and the platform it publishes to. See §5 step 4's note for the full mechanics (auto-attach, the manual fallback, readiness gating).

1. **Create account** — sign up / log in
2. **Create business** — business profile (see §7 for exact fields)
3. **Select objective** — campaign goal (see §7 for the exact value set — maps to Meta Ads campaign objectives); no product/audience picker at this point, since neither necessarily exists yet
4. **Describe product & define audience** — what the business sells, and who buys it (see §7 for exact fields); auto-attaches to the campaign from step 3 that this step exists to unblock (see §5 step 4's note for the full mechanics)
5. **Upload images** — product/brand image assets, used as ad creative input
6. **Connect Meta Ads** — OAuth into the user's Meta Business account, select ad account + Page
7. **AI generates strategy** — targeting, budget, objective-specific recommendations grounded in the business profile + product description; requires the campaign to have a product and audience attached (see §5 step 4's readiness-gate note)
8. **AI generates ads** — ad copy variants + ad creative (composed from uploaded images and/or AI-generated), grounded in the strategy
9. **User approves** — review the generated strategy + ads; a single explicit **"Approve & Publish"** action is the only thing that triggers step 10 — approving never silently publishes on its own (see the checkpoint note under §5 step 8)
10. **Campaign goes live** — publish via the Meta Marketing API (create campaign / ad set / ad)
11. **Dashboard shows results** — pull performance metrics back from the Meta Ads Insights API

**Assumption (flag if wrong):** billing/subscriptions and credit metering are *not* part of this MVP loop — the priority is proving the core value loop (account → live campaign → results) before monetization. Billing moves to post-MVP (§4). The plan/pricing table in §3 is the target monetization model once billing is built, not an MVP requirement.

## 4. Out of scope for MVP (explicitly deferred)

- **Billing/subscriptions/credits** — no payment gate in MVP; all AI generation is unmetered until billing lands post-MVP
- **Google Ads / TikTok Ads publishing** — Meta Ads only for MVP; other platforms require separate API integrations, deferred
- **Agency tier / multi-client management**
- **Team seats / multi-user per business**

**Known external dependency / risk:** Meta Marketing API access requires Meta App Review and Business Verification before the app can create live campaigns on a user's behalf beyond a small set of test users. This is an external approval process outside our control — build the integration against Meta's sandbox/test mode first, and treat App Review as a launch blocker to track separately, not an engineering task we can shortcut.

**Resolved (2026-09-01):** the session cookie now switches to `samesite=none; secure` in production (`app/api/auth.py`'s `_cookie_cross_site_attrs()`), covering the cross-site relationship between the separate Render frontend/backend subdomains; dev keeps `samesite=lax` with no `secure` flag since localhost frontend/backend share an origin. `render.yaml` now also sets `FRONTEND_URL`/`BACKEND_URL`/`CORS_ORIGINS` (backend) and `VITE_API_URL` (frontend) to Render's default `<service-name>.onrender.com` hostnames — `CORS_ORIGINS` in particular is required alongside the cookie change, since a credentialed cross-site request is blocked by CORS before the cookie's `SameSite` attribute is ever consulted. If either service ends up on a different hostname than Render's default pattern, these four values need to be updated to match.

**Resolved (2026-09-02):** the first real Render deploy attempt failed — `schema.prisma`'s `datasource` was still hardcoded to `provider = "sqlite"`, which rejects a Postgres `DATABASE_URL` outright. This had been carried as an implicit to-do since §6/§1's "SQLite dev → Postgres prod" line was written, never actually executed. Fixed with a second, mirrored schema file, `backend/prisma/postgres/schema.prisma` (`provider = "postgresql"`, otherwise identical models) with its own migration history — Prisma migration SQL is dialect-specific, so a single schema.prisma can't serve both providers; `render.yaml`'s build now points `prisma generate`/`migrate deploy` at the Postgres file via `--schema`. See README.md's Database schema changes section for the process to keep both schemas in sync going forward.

Two further issues surfaced getting that first real deploy live, both resolved 2026-09-02:
- **Region mismatch:** the free-tier Render Postgres instance (`sales-guru-db`, 30-day expiry, expires 2026-10-01 unless upgraded) landed in Ohio while the web services are in Oregon — Render's private network doesn't span regions, so the backend couldn't reach the DB's Internal Database URL (`P1001: Can't reach database server`). Fixed by pointing `DATABASE_URL` at the database's *External* Database URL instead (works over the public internet regardless of region). Worth revisiting later — recreate the DB in Oregon and switch back to the Internal URL for lower latency and no public egress, once there's real data worth the migration.
- **Missing query engine binary at runtime:** the build succeeded (migrations applied cleanly) but the app crashed on startup with `prisma.engine.errors.BinaryNotFoundError` — `prisma-client-py`'s default binary cache lives under the build user's home directory (`~/.cache/prisma-python`), which is outside the project directory Render actually ships to the running instance, so the query engine binary downloaded at build time wasn't there at boot. Fixed by setting `PRISMA_BINARY_CACHE_DIR=.prisma-cache` (project-relative) in `render.yaml`.

Once live, manual click-through testing against the real production deploy (2026-09-02: signup, business/product/audience creation all verified working end-to-end against the real Postgres DB) surfaced one more deploy-config bug, also resolved 2026-09-02:
- **Deep links 404 on the static frontend:** `App.tsx` uses react-router's `BrowserRouter` (real History API routes), but Render's static site serves files directly — hitting a route like `/businesses/:id` via a hard refresh or a shared link 404s, since no such file exists on disk (only `/index.html` does). Fixed with a Render static-site rewrite rule in `render.yaml` (`source: /*` → `destination: /index.html`) so every path falls through to the SPA shell and React Router takes over client-side.

**Resolved (2026-09-02):** `MetaConnection.accessToken` (build step 6) is now encrypted at rest — unlike `User.hashedPassword`/`Session.tokenHash`, this token has to be usable later for real Marketing API calls, not just verified, so it can't be a one-way hash. Uses Fernet symmetric encryption (`cryptography` package, new dependency) via `app/core/crypto.py`, keyed by a new `META_TOKEN_ENCRYPTION_KEY` env var. Every read site was routed through a single shared, decrypting fetch — `app/core/meta_connection.py`'s `get_meta_connection()` — instead of calling `db.metaconnection.find_unique` directly, so `connection.accessToken` stays a plain string everywhere it's already used downstream (`publish.py`, `optimization_jobs.py`, `strategy.py`, `metric.py`, `campaign.py`); only that one fetch helper and the single OAuth-callback write site (`app/api/meta.py`) needed to change.

**Resolved (2026-09-19):** `render.yaml` referenced `ANTHROPIC_API_KEY`/`META_APP_ID`/`META_APP_SECRET`/`META_REDIRECT_URI` only in a comment — never as real `envVars` entries — so a fresh Blueprint deploy left them unset with no error until a real request needed them (Strategist/Creative Agent calls, Meta OAuth). Declared all four as `sync: false` so the Render dashboard actually prompts for values. Also closes part of the Meta App Review blocker noted above: the app's Basic Settings page needs a Privacy Policy URL, Terms of Service URL, and Data Deletion Instructions URL, all pointing at a real public URL rather than `localhost` — `/privacy`, `/terms`, `/data-deletion` (build step 2's terms-acceptance note below) now exist to serve as those three once deployed. Category and app icon still have to be set directly on Meta's own app dashboard; App Mode (Development → Live) itself is still untried.

## 5. Build order (one component at a time, each fully working before the next)

1. **Foundation** — React 19 + TS + Vite frontend, Python (uv) + FastAPI backend, Prisma schema (SQLite dev → Postgres prod) via `prisma-client-py`, test/lint/CI tooling. *(done)*
2. **Auth** — `POST /auth/signup` (auto-provisions Organization, auto-logs in), `/login`, `/logout`, `/me`; DB-backed sessions via httpOnly cookie, tokens hashed at rest. Frontend: `/login`, `/signup` pages, `AuthProvider`/`useAuth`, route guards. *(done)*

   **Legal pages + terms acceptance at signup (confirmed 2026-09-19, `done`):** `/privacy`, `/terms`, `/data-deletion` — public, ungated frontend routes (needed so Meta's App Review can reach them from a real public URL, and so signup can link them), linked from a new site-wide `SiteFooter`. Content is grounded in what the app actually collects/does, including an explicit "how we use data obtained through Meta" section (only for the user's own campaigns, never sold, never used to target anyone else) and an honest data-deletion procedure — draft status noted in a code comment only, not in the visible page text, since legal review is still pending.
   - `SignupRequest` gains a required `termsAccepted: bool`, rejected with 422 (via a field validator, not just "missing field") if false or absent — the frontend pairs this with a required, unchecked-by-default checkbox linking all three documents (opens in a new tab), disabling submit until checked. `User.termsAcceptedAt`/`termsVersion` (both schema files + migrations) record acceptance against a single `TERMS_VERSION` constant (`app/core/terms.py`, starts `"2026-09"`) — bumping that one value is what forces every account to re-accept after a future material change to the documents, not resetting the timestamp by hand.
   - **Existing accounts** (`termsAcceptedAt` null, or an old `termsVersion` — in practice only ever an account that predates this feature) hit a one-time, full-page `TermsAcceptancePrompt` on next login, gated at `ProtectedRoute` — the single choke point every authenticated route already goes through — rather than blocking login itself or any other endpoint. `POST /auth/accept-terms` is the only way to clear it.
   - **Known gap, queued, not yet built:** "delete a business" is a soft delete (`deletedAt`, `app/api/business.py`) — the Data Deletion page is honest about this rather than claiming self-serve erasure that doesn't exist. A real-erasure job (hard-delete a soft-deleted business and all its data — photos, logo, Meta tokens, campaigns, metrics — after a 30-day window) is queued for later, after the carousel work and plan limits.
3. **Business + product + audience onboarding** — Business (dashboard: list + create form), Product, and Audience (both on a `/businesses/:id` detail page, via `ProductsSection`/`AudiencesSection`) all done, backend + frontend. `GET /businesses/{id}` added for the detail page.

   **Product image upload, closing this step (confirmed 2026-09-02, `done`):** real photo uploads only — AI-generated images are explicitly deferred to a later pass (the Creative Agent already produces an `imagePrompt` per variant, so that hook exists whenever it's picked up). **Storage: Option A, image bytes in the database** (`ProductImage.data: Bytes` + `contentType`, confirmed 2026-09-02) — no object storage account/credentials needed at MVP scale, survives Render's ephemeral filesystem since Postgres persists, and the app's existing "no new infrastructure" precedent (APScheduler over Redis/Celery, step 10) already established this bias. `POST/GET/DELETE .../products/{id}/images` (`app/api/product_image.py`) are session-authed and ownership-scoped like everything else.
   - **A public, unauthenticated serving route is unavoidable and deliberate:** `GET /product-images/{id}` has no `get_owned_business` check — same split as `app/api/meta.py`'s `router`/`callback_router` (the Meta OAuth callback is hit directly by Meta, not through the frontend). Meta's own servers used to fetch this URL directly for `link_data.picture`; as of the real-image-upload pass below they instead get the bytes uploaded ahead of time, but the route stays public — the frontend still renders these images directly (`<img src>`), unauthenticated, same as any other externally-hosted image URL. The id in the URL is an unguessable cuid, not a sequential index, and product images are meant to be shown to the public in ads anyway, so there's no meaningful confidentiality loss.
   - **New `BACKEND_URL` setting** (`app/core/config.py`, mirroring the existing `FRONTEND_URL`) builds the absolute, publicly-fetchable image URL — a relative path won't do, since Meta's servers (not the browser) fetch it. Defaults to `http://localhost:8000` in dev, which Meta genuinely cannot reach — image-backed ad creatives only really work once deployed. **Set in `render.yaml` as of 2026-09-01** (see §4's cookie/CORS resolution note above) to Render's default `<service-name>.onrender.com` hostname.
   - **Wired into creative selection, not publish:** `POST .../creatives/{id}/select` (`app/api/creative.py`) auto-attaches the campaign's product's primary uploaded photo as `Creative.imageUrl`/`Creative.productImageId` when one exists and the creative doesn't already have one — the natural checkpoint moment before publish, and the point where the frontend can show the user what image the ad will actually use (`imageUrl` is now exposed on `CreativeResponse`, previously absent).

   **Multi-photo upload moved into `ProductForm`, required to publish, campaign-list thumbnails, vision-grounded ad copy, and real Meta image upload (confirmed 2026-09-09, `done` — supersedes several specifics of the bullet above):**
   - **Upload moved into `ProductForm` itself**, shared by onboarding, the new-campaign wizard, and product swap/edit — not a separate block on `ProductsSection` anymore. Multiple photos, thumbnails, remove, reorder via move-earlier/move-later (first = primary). `ProductImage` gained a `position: Int` field (schema + migration, both SQLite and hand-written Postgres) as the actual ordering mechanism — `createdAt` is immutable and can't represent a user reorder; a new upload appends past the current max position, never a plain count (which would collide after a deletion).
   - **Upload validation narrowed and raised:** JPG/PNG only (dropped webp — narrow enough that `app/services/image_dimensions.py`, a hand-rolled dependency-free header parser, can read width/height without pulling in Pillow), 8MB cap (was 5MB), minimum 600px on the short side (blocking), and a non-blocking warning when the aspect ratio falls outside Meta's recommended 1:1–4:5 range. **Not yet verified: the dimension reader doesn't account for EXIF orientation** — a phone photo stored portrait-but-rotated (landscape pixel dimensions plus a rotation tag) would report the wrong short side; flagged, not yet fixed.
   - **A product with zero uploaded photos can no longer be published at all:** `POST .../creatives/{id}/select` now 428s outright ("Add at least one product photo before selecting an ad to publish") if the campaign's product has no photos — publishing image-less, previously the default, is no longer possible via the normal flow. This closes the "known simplification" the step-8 note below used to describe.
   - **Campaign list shows a thumbnail** — `ProductResponse.primaryImageUrl` (computed from the product's position-0 photo) lets `CampaignsSection` show each campaign's product photo next to it, so campaigns are visually distinguishable at a glance, without a separate images fetch per row.
   - **Vision-grounded Creative Agent:** `generate_creatives` (`app/services/creative.py`) now takes the product's primary photo and, when present, sends it to Claude as an image content block alongside the existing text grounding (description/features/benefits/strategy) — no model swap needed, Claude already reads images. A short prompt note tells the model to actually look at it, since a forced tool-use call otherwise gives no cue to attend to an image block over the text. Fake mode (`FAKE_LLM`) is unaffected — it returns the canned batch before ever touching the image. Verified against the real Anthropic API (the opt-in `real-llm-publish.spec.ts`, not just a mocked test) — a genuine vision-grounded generation flowed through select→publish successfully.
   - **Real Meta ad image upload replaces the bare-URL `link_data.picture` mechanism.** New `upload_meta_ad_image` (`app/services/meta.py`) uploads the raw bytes to `.../adimages` and returns an `image_hash`, which `create_meta_ad_creative` now sets as `link_data.image_hash` instead of a fetchable picture URL — Meta no longer has to fetch our server at all. Faked in `FAKE_META` mode like every other Graph call.
   - **`Creative` gained a `productImageId` field** (schema + migration, both DBs) — `imageUrl` alone (our own `/product-images/{id}` URL) isn't enough to fetch raw bytes for the real Meta upload above, so `select_creative` now stores the actual photo id alongside the derived URL, on both the auto-attach and explicit-photo-choice paths. Not a `@relation` (deliberately, same as `sourceProductId`) — a missing reference is handled explicitly in application code instead (the next bullet), not enforced as a DB-level FK constraint.
   - **Publish-time failure modes, deliberately asymmetric (confirmed 2026-09-09):** if `productImageId` names a photo that's since been deleted (`ProductForm`'s photo-removal UI has no in-use guard yet — a known, flagged gap), publish now fails loudly with a clear `MetaConnectionError` (campaign marked `FAILED`, retryable) rather than silently falling back to image-less — a stale reference is a real data problem, not "no photo was ever chosen." The only permitted image-less path is a creative with no `productImageId` at all (a legacy creative predating this field, or — no longer reachable via the normal flow given the 428 gate above — a campaign whose product genuinely had none): that case only logs a warning and proceeds. A real Meta API failure from the `adimages` upload call itself (e.g. Meta rejecting the image) is never caught either — it propagates uncaught, exactly like every other `meta.*` call in `publish_campaign_to_meta`, failing the publish the same way.
   - **A public, unauthenticated serving route is still needed** even though Meta no longer fetches it — the frontend renders every product photo directly via this URL (thumbnails, `ProductForm`'s manager, the selected-ad preview), so it stays public and unauthenticated for that reason instead now.
   - **`upload_meta_ad_image`'s real request shape, confirmed against a live ad account 2026-09-09 across three separate real-API failures — none obvious, all fixed the same day:**
     1. Meta's documented alternative to a real file upload — a `bytes={"key": "<base64>"}` form field sent as plain `application/x-www-form-urlencoded` — failed outright (`error_subcode` 2446496, "We could not process the image you have uploaded"). Every official example of this call actually uses `-F` (multipart/form-data) in curl, i.e. a real file part, not that alternative.
     2. Switching to a multipart file part fixed that, but with no explicit filename/content-type on the part, Meta couldn't identify it as an image at all (`error_subcode` 1487411, "The type of file is not supported") — httpx has no extension to guess a MIME type from a bare field name, so it silently fell back to `application/octet-stream`. Passing the already-known `content_type` (`ProductImage.contentType`) explicitly — both as the filename's extension and the part's real content-type — fixed this.
     3. With the upload itself finally succeeding, a *third* surprise: Meta keys the response's `images` object by the filename actually used, not by the multipart field name, so the original hardcoded `body["images"]["image"]` lookup raised an uncaught `KeyError`. Reading the response's one value directly (exactly one file is ever uploaded per call) instead of a specific key fixed this without needing to know or guess Meta's exact echoed key at all.
     Also added: every Meta API error now includes which endpoint was called plus `error_user_msg`/`error_subcode`/`fbtrace_id` when Meta provides them (`app/services/meta.py`'s `_raise_for_meta_error`) — previously every failure just said "Meta API call failed: `<generic top-level message>`", with no way to tell even which of the ~5 publish-time Graph calls had failed; this is what made diagnosing the three failures above tractable at all.
   - **Currently blocked one step further, by Meta's own app configuration, not by anything in this codebase:** with the upload fixed, the real live-publish attempt got all the way through campaign → ad set → ad-image creation, then failed at `POST /adcreatives` with `error_subcode` 1885183: "Ads creative post was created by an app that is in development mode. It must be in public to create this ad." The Meta app ("Sales Guru," see `project_sales_guru_meta_app_review` memory) is still in Development Mode, not Live — switching requires the same four Basic Settings fields (Privacy Policy URL, Terms of Service URL, Data Deletion Instructions URL, Category + icon) already blocking Tech Provider status, all of which need a real public URL (i.e., the Render deploy, not `localhost`). Unconfirmed whether flipping Development→Live alone (vs. also needing Advanced Access/App Review on `ads_management`) is sufficient for this single-tenant, own-account use case — find out by actually completing Basic Settings and trying the toggle.

   **Product editing, campaign product swapping, and creative-staleness detection (confirmed 2026-09-08, `done`):** a product could be created but never updated, and a campaign could bind a product exactly once — no way to correct a typo'd description/price/URL, or to swap an already-attached product for a different one, short of editing the database directly.
   - **`PATCH /businesses/{id}/products/{id}`** (`app/api/product.py`) is a partial update — only fields present in the body change (`model_dump(exclude_unset=True)`, not a "null means unchanged" convention, since `url` must stay nullable), and `url` still routes through the one `validate_destination_url` helper. Products are reusable across campaigns (documented in `CLAUDE.md`): this endpoint is for correcting the same item being sold, never for repurposing a product record into a different item — swapping the campaign's product (below) is the mechanism for that instead.
   - **`update_campaign`'s manual product-binding path no longer blocks on a URL-less product** the way `create_campaign` still does — swapping a campaign onto a different product always succeeds; `CampaignResponse.needsDestinationUrl` (computed at read time from the campaign's current product + objective) warns instead, since a swap is a correction in progress, not a fresh creation that should refuse to save an inconsistent state.
   - **`Creative` gains a `sourceProductId`/`sourceDescription`/`sourceUrl` snapshot**, populated whenever a batch is generated or regenerated (`app/api/creative.py`'s `create_creatives`, step 6). `is_creative_stale()` (`app/services/creative.py`) is the single place that compares a creative's snapshot against its campaign's *current* product — never stored as a flag, always computed at read time, surfaced as `isStale` on every `CreativeResponse`. A campaign with no product attached is never "stale," just "no product," a distinct case. Editing a product or swapping a campaign onto a different one both make its already-generated creatives read as stale from that point on; neither action deletes old creatives — kept for history.
   - **Publish is blocked once the selected creative is stale** (step 8's `publish_campaign`) — a clear message points at regenerating rather than silently shipping outdated ad copy live.
   - Frontend: `ProductsSection` gained an inline Edit/Save/Cancel row (a shared `ProductForm` component, reused in create and edit mode); every campaign always shows its current product with a "Change product" control (previously only shown while `DRAFT` and missing one) offering existing products or "Add new product"; a stale-ads banner with a "Regenerate" button appears on any campaign with stale creatives.
   - **Postgres migration provenance:** hand-written to mirror the SQLite migration (no external Postgres reachable mid-session), then verified 2026-09-08 by running `prisma migrate dev --schema=prisma/postgres/schema.prisma` for real against the Render database — applied cleanly, no drift, no new migration generated, confirming it matches what Prisma itself would have produced.

   **Business logo upload — first piece of "brand DNA" (confirmed 2026-09-10, `done` for storage/upload only):** the create-business form (renamed "Company Information") gained a Logo field, first field on the form, ahead of Name — the intent (per the user) is a foundation for the AI to generate consistent, on-brand ads, not a cosmetic add. Staged client-side and uploaded right after the business is created, same pattern as `ProductForm`'s staged photos (there's no business id to upload against until the create call returns). Storage: same Option A approach as `ProductImage` — `Business.logoData: Bytes` + `logoContentType`, one replaceable pair of columns rather than a separate table, since a business only ever has one logo. `POST /businesses/{id}/logo` (upload/replace, session-authed) and a public, unauthenticated `GET /business-logos/{id}` (`app/api/business.py`) — same public-serving reasoning as product photos, for whenever a consumer other than our own frontend (the Creative Agent, or eventually Meta) needs to fetch it directly. Once uploaded, the frontend shows it as a compact identity card (circular avatar, business name, website, edit button) rather than the plain square thumbnail used for product photos.
   - **Discovered as a side effect, unrelated to the logo itself:** generating this migration surfaced that production Postgres was missing the `PasswordResetToken` table entirely — it exists in the SQLite dev schema (added when forgot-password shipped) but no matching Postgres migration was ever generated for it, so the real production database never actually got this table. Fixed with its own isolated migration, shipped alongside this change but logically unrelated to it.

   **Brand Profile — "brand DNA" grounding for the Strategist/Creative Agents (confirmed 2026-09-11, `done`):** a `BrandProfile` model, one per business (`businessId` unique, same 1:1 shape as `MetaConnection`) — `description`/`idealCustomer`/`voiceTraits`/`pricePositioning` required, `brandPhrases`/`avoidPhrases`/`tagline`/`competitors`/`exampleCopy` optional. `voiceTraits` is a fixed 8-value list (luxurious/playful/minimal/warm/bold/artisanal/edgy/professional, multi-select) and `pricePositioning` a fixed 4-value list (affordable/mid/premium/luxury) — both served via `GET /options` (`voiceTraits`/`pricePositionings`), same fetch-from-backend pattern as every other fixed list. `voiceTraits` itself is stored as a JSON-serialized string (SQLite has no native array type — same "serialize at the app layer" convention as `Strategy.content`). `POST/GET/PATCH /businesses/{id}/brand-profile` (`app/api/brand_profile.py`); `logo_url` rides along on the response, computed from the parent business.
   - **Onboarding step, not just a settings field.** `BrandProfileSection`/`BrandProfileForm` (frontend) render as a new "Brand" step on `BusinessDetailPage`, right after Company Information and ahead of the campaign-objective step — the first gate shown, and (unlike the other onboarding gates) it stays visible alongside whichever step comes after it once a profile exists, not just once onboarding is fully done, since "editable later from the business page" was an explicit requirement — there's no page a user could otherwise reach it from if it only showed once, all the way at the end, behind a real Meta OAuth connection this test suite (and most real users, until Meta Business Verification clears) can't get past.
   - **A shared "Brand voice" prompt block** (`app/services/brand_voice.py`'s `brand_voice_lines`) is used, unchanged, by both `app/services/strategist.py` (folded into `_business_product_audience_lines`, so both `TEST_PLAN` and `DATA_DRIVEN_STRATEGY` prompts get it) and `app/services/creative.py` (`_build_prompt`) — one function so the two agents can't describe the brand differently. States the voice traits/price positioning as plain instructions, quarantines every free-text field (`app/services/prompt_safety.py`, same convention as `Business`/`Product.description`), and gives `avoidPhrases` (when set) an explicit "NEVER use, under any circumstance" instruction, distinct in wording from `brandPhrases`'s softer "use naturally where they fit." Returns `[]` with no profile at all — a pure no-op, not a placeholder note — so a campaign generated before a business fills this in behaves exactly as before this step existed.
   - **The Creative Agent also grounds in the business's logo as a second vision input**, when uploaded (`Business.logoData`/`logoContentType`, from the business-logo-upload step above) — sent as an image content block ahead of the product's own primary photo (when both exist), with an explicit prompt note that it's a visual style cue only (color/mood), never a literal subject to describe. This is the "actual on-brand-ads payoff" the logo-upload step's own note above was waiting on — now wired in.

   3.6. **Objective-aware CTA, enforced at the schema level (confirmed 2026-09-12, `done`):** a Sales campaign coming back with `LEARN_MORE` on one variant and `GET_OFFER` on another (the prompt alone wasn't enough — nothing tied the two together) is now impossible. `ALLOWED_CTAS_BY_OBJECTIVE`/`DEFAULT_CTA_BY_OBJECTIVE` (`app/schemas/creative.py`) key off the app's real 5-value `Objective` enum — SALES→{SHOP_NOW, GET_OFFER}, LEADS→{SIGN_UP, CONTACT_US}, TRAFFIC→{LEARN_MORE, SHOP_NOW}, MESSAGES→{MESSAGE_PAGE}, AWARENESS→{LEARN_MORE} — leaving `SUBSCRIBE`/`DOWNLOAD`/`BOOK_NOW` unreachable by the agent (no objective maps to them; left in the CTA enum rather than removed, for historical rows and a possible future objective). `GeneratedCreativeBatch` (the tool-call schema itself, not just a post-hoc check) enforces: every variant in a batch shares one CTA; every variant has a distinct `creative_angle` (case-insensitive; freeform, not a fixed enum — a fixed jewelry-style vocabulary doesn't generalize across the app's 10 industries, so this stays consistent with `Strategy.creative_angles`, which the prompt already draws from); the shared CTA is one the objective allows; and `GET_OFFER` specifically requires a non-empty standing promotion (`BrandProfile.offer`, new field, see below) that every variant's own primary text actually references (a loose, deliberately fuzzy keyword check — the model paraphrases rather than quoting the offer verbatim). The objective/offer checks run only when the caller passes Pydantic validation context (`app/services/tool_use.py`'s `parse_tool_input` extended to thread one through) — `generate_creatives` always does; the coercion fallback's own structural-only re-check deliberately doesn't. On a first failure, `generate_creatives` retries once with the validation error appended to the prompt; a second failure force-coerces every variant to the objective's default CTA and truncates any still-over-length text at a word boundary, rather than failing generation outright.
   - **Five Meta ad-text slots, with real per-slot character limits enforced (not just documented):** `headline` ≤40, `body_text`/primary text ≤125 (Meta's own "See more" cutoff), `description` ≤30 and now nullable (`Creative.description`, both Prisma schemas — not every business has a proof point that fits every variant, and padding it with filler was worse than omitting it; `create_meta_ad_creative`, `app/services/meta.py`, now omits `link_data.description` entirely when null, letting Meta auto-generate one from the link, same as when nothing was ever given). `body_text`/`image_prompt`/`video_prompt` field names are unchanged (confirmed with the user — a `primary_text` rename would've touched ~14 files including a DB migration for no behavioral gain; `image_prompt`/`video_prompt` still exist and are untouched, unrelated to the ad-text-slot limits).
   - **`BrandProfile` gained two fields** (migrated on both SQLite and Postgres): `proofPoints` (JSON-serialized string array, same "no native array type" convention as `voiceTraits`) and `offer` (nullable string) — the business's own standing promotion, e.g. "20% off first order with WELCOME20." Deliberately distinct from the pre-existing, per-campaign `Strategy.offer` (LLM-generated, always present, a different kind of "offer" entirely) — the Creative Agent's prompt labels the two separately ("Standing promotion (from brand profile)" vs. "Campaign strategic offer") so the model can't conflate them, and only the former gates `GET_OFFER` eligibility. Exposed on the Brand Profile create/update endpoints and `BrandProfileForm` (one proof point per line in a textarea, not a dynamic add/remove list — consistent with every other free-text field on that form).
   - **Prompt order rebuilt** (`app/services/creative.py`'s `_build_prompt`): objective + the exact allowed CTA set stated explicitly (with a `GET_OFFER`-usability note either way) comes first, then the brand voice block (existing `brand_voice_lines`, plus proof points and the standing/strategic offer distinction read directly rather than folded into that shared, Strategist-agent-facing helper), then product, then a new industry-keyed reference-angle-structure block (`_ANGLE_TEMPLATES_BY_INDUSTRY`, a plain dict so per-industry templates can be added later) — Fashion/Jewelry gets "product + material + trust line" / "social proof + product" / "offer + urgency"; every other industry falls back to a generic "benefit + trust line" / "social proof + product" / "offer + urgency" set. The business's own website is stated as "shown automatically as the display link, never write the domain into the copy" rather than omitted or left for the model to guess at.

   **Two-mode agent (confirmed 2026-08-31):** the Strategist Agent (`app/services/strategist.py`) generates one of two distinct plan shapes, decided by the backend (never the LLM), same "backend decides, agent never invents it" reasoning as `Campaign.objective` being fixed input: **TEST_PLAN** for a business with no meaningful advertising history, **DATA_DRIVEN_STRATEGY** for one with real historical performance (a full strategy plus `keyLearnings`/`recommendedAdjustments`/`scalingTrigger` — distinct from the live Optimization Agent, step 10 below, which reacts to *this* campaign's own live metrics rather than *other* past campaigns).

   **plan_type decision (`app/api/strategy.py`), in priority order:**
   1. **Real Meta ad-account history wins over everything** — once a business connects Meta Ads (step 6), `fetch_account_historical_performance` (`app/services/meta.py`) pulls lifetime per-campaign insights for the *whole ad account* (not just campaigns Sales Guru itself published — catches a business that advertised on Meta before ever using this product). Any nonzero spend at all (`has_meaningful_history`, no dollar threshold) means DATA_DRIVEN_STRATEGY, grounded in those real numbers.
   2. **Otherwise, a one-time self-reported answer** — `Business.hasPriorAdvertisingExperience`, asked once (in the Strategy-generation UI, "Has this business run marketing/ad campaigns before?") and stored permanently once answered; never asked again for that business. Real Meta history, if it later appears, still overrides even a stored "no" — self-report never wins over evidence.

   **TEST_PLAN is a structured advertising experiment, not just two recommended audiences (confirmed 2026-09-01, "Phase A" of a larger redesign — Phase B, an Optimizer that consumes this plan against real results, `done`; Phase C, real two-adset Meta publishing plus real Meta interest targeting, `done`, confirmed 2026-09-02 — see the "Phase C" bullets below):**
   - **Two audience variants, always.** **Variant A (`broad_baseline`)** is entirely backend-constructed — deliberately empty/unconstrained targeting (Meta's Advantage+-style automated delivery, where the objective supports it), no invented interests, the experiment's control. **Variant B (`hypothesis_audience`)** is the only thing the LLM designs: one specific, non-interest-stacked audience grounded in the real product/business/audience data — simple enough to interpret, specific enough to test a real hypothesis. `app/schemas/strategy.py`'s `AudienceVariant`/`GeneratedTestPlanFields` encode exactly which sub-fields are backend-fixed vs. LLM-generated.
   - **One primary hypothesis, falsifiable.** `hypotheses: [TestHypothesis]` — `baseline_variant`/`test_variant`/`primary_metric` (`cac`)/`secondary_metrics` (`ctr`, `cpc`, `add_to_cart_rate`, `conversion_rate`, `roas`) are backend-fixed (every TEST_PLAN compares the same two variants the same way); only the LLM-generated `statement` text varies, so it can name the actual audience specifics rather than reading as a template sentence. The purpose is to collect evidence, not assume a winner — Sales Guru never claims to know the answer before the experiment runs.
   - **Budget/duration are a backend business rule, not an LLM recommendation or an absolute advertising truth** (confirmed 2026-09-01): `_compute_test_daily_budget` (`app/services/strategist.py`) uses `DEFAULT_TEST_BUDGET` ($50/day) and `DEFAULT_TEST_DURATION` (10 days) when the product has no computable unit economics; otherwise the daily budget is anchored to the product's own `target_cac` (a productive test should buy roughly one conversion a day at that rate), clamped to `[MIN_TEST_BUDGET, MAX_STARTING_BUDGET]` = `[$20, $75]`/day (constants in `app/schemas/strategy.py`). The LLM is told the resulting numbers as context, never asked to set them. `dailyBudget` is a **per-variant** rate — each of the TEST_PLAN's two `audienceVariants` gets its own AdSet spending at this rate, so actual total daily spend is `dailyBudget × 2` (confirmed 2026-09-01). `totalBudget` is backend-computed as `dailyBudget × audienceVariants.length × durationDays` (e.g. $50/day × 2 variants × 10 days = $1,000, not $500).
   - **`success_criteria` splits leading indicators (CTR, CPM, add-to-cart rate — a useful read with little data) from economic indicators (conversion rate, CAC, ROAS — need more volume)** — a cold-start test shouldn't define success exclusively as "hit target ROAS." Every criterion carries a `direction` (`higher_is_better`/`lower_is_better`, from `benchmarks.py`'s `METRIC_DIRECTIONS`) so "better" is always known even for metrics with no numeric benchmark yet (CPC, ROAS, add-to-cart rate).
   - **`benchmark` (industry-wide) and `business_target` (this specific business's own economics) are two separate numbers on every criterion, never blended into one** (confirmed 2026-09-01) — a $2,000 product at 50% margin needing "CAC below $100" is a business target that has nothing to do with what the broader jewelry industry typically sees; an earlier draft of this design picked "whichever is more conservative" between the two, which silently hides one fact behind the other. `benchmark_context` (the industry side) and `unit_economics` (the business side, below) stay as separate top-level fields on the plan for the same reason.
   - **`decision_rules`** — fixed `{condition, action}` pairs (e.g. `"hypothesis_audience has lower CAC with sufficient conversion volume" → "prefer_hypothesis"`) comparing the two named variants, telling a future Optimizer what to do with the result; never LLM-generated, so they stay consistent across every test plan and machine-matchable on `action`.
   - **`baseline_metrics`** — the full normalized metric shape (`impressions`/`reach`/`spend`/`cpm`/`clicks`/`ctr`/`cpc`/`landing_page_views`/`add_to_cart`/`add_to_cart_rate`/`conversions`/`conversion_rate`/`cac`/`purchase_value`/`roas`), all `null` at plan-generation time — `null` means unavailable/not-yet-collected, never zero. This is the shape real Meta metrics will eventually populate (Phase B); not every campaign objective produces every metric.
   - **`data_source`** — explicit provenance tagging which fields came from business facts, historical Meta data (always empty for TEST_PLAN — that's what routes a business to DATA_DRIVEN_STRATEGY instead), industry benchmarks, or AI-generated content, per the product requirement to never present a benchmark estimate as actual business performance.

   **Unit economics (confirmed 2026-08-31, extended 2026-09-01 with `breakeven_roas`; `app/services/unit_economics.py`):** when the campaign's product has both `price` and a nonzero `margin` set,
   ```
   gross_profit = price * margin        # margin is a fraction, e.g. 0.4 for 40%
   breakeven_cac = gross_profit
   target_cac = gross_profit * 0.33
   breakeven_roas = 1 / margin          # price cancels out
   ```

10. **Campaign optimization agent** — AI recommends pausing an underperforming ad, increasing budget on a well-performing one, or decreasing budget on a struggling one, grounded in the campaign's `Metric` history; a LOW-risk, high-confidence budget nudge can apply itself, everything else waits for an explicit checkpoint. Was out of scope for MVP (§4, old revision) until real performance data started flowing in step 9 — now buildable. *(done)*

    **Architecture (confirmed 2026-08-09):** two APScheduler jobs, in-process, no new infrastructure (no Redis/Celery/external cron — same Prisma/SQLite-dev/Postgres-prod DB as everything else, not a separate store):
    - `collect_metrics_for_all_live_campaigns` (every 15 min) — pure metrics collection for every live, Meta-connected campaign, no decisions made. Same Insights pull as step 9's manual "Refresh results," just scheduled.
    - `evaluate_all_live_campaigns` (every 60 min) — gate-checks each live campaign against **Event + Time + Data Sufficiency** (`has_sufficient_data`: hours since last check ≥6h AND spend since last check ≥$20 AND clicks since last check ≥30, all three ANDed) before spending an LLM call, so a campaign isn't re-analyzed off a normal fluctuation or before it has enough signal. This collapses the originally-discussed separate "4-6h lightweight check" and "24h deep optimization" tiers into one job with an internal ~24h-per-campaign cadence (`MIN_HOURS_BETWEEN_RECOMMENDATIONS`), rather than building a second, under-specified lightweight-analysis pathway — a scoped simplification of the reference 3-tier design, not the full spec.

    Once the gate passes, the agent computes real trend windows (24h/3d/7d deltas, via `compute_trend_windows`/`nearest_metric_at_or_before` diffing the latest cumulative `Metric` snapshot against the closest prior one) rather than reasoning over Meta's raw lifetime-to-date numbers — comparing recent performance against a spread of history is what prevents "CTR dipped this morning → PAUSE" reactions to noise. The LLM (forced tool-use, same pattern as Strategist/Creative) returns a structured recommendation — `action_type`, `reasoning`, `confidence` (0-1, self-assessed), `risk` (LOW/MEDIUM/HIGH, self-assessed), `suggested_budget` (optional) — never a single accept/reject question. Any budget suggestion is capped by a backend guardrail (`apply_budget_guardrail`, max ±20% change) before it's ever stored, never trusted raw from the LLM.

    `app/services/optimizer.py` is the pure agent (gate logic, trend computation, the LLM call, guardrail) with no DB access; `app/services/optimization_jobs.py` is the DB-touching orchestration layer the scheduler (`app/core/scheduler.py`) and the manual "generate now" endpoint both call — same pure-service-vs-orchestration split already used for publish (`app/services/meta.py` vs. `app/services/publish.py`). `apply_recommendation` (in `optimization_jobs.py`) is the single place that actually calls Meta for a recommendation, shared by the manual Approve click and the auto-apply path below.

    **Checkpoint requirement (confirmed 2026-08-08, tiered 2026-08-09):** `requiresApproval` is computed by the backend (`compute_requires_approval`), never taken from the model. Risk is a hard gate, not something confidence can override:
    - **HIGH risk → always a mandatory checkpoint**, regardless of confidence (e.g. a $50/day → $500/day jump stays mandatory even at high confidence).
    - **LOW risk + confidence ≥ 90% (`AUTO_APPLY_CONFIDENCE_THRESHOLD`), on a budget action (`INCREASE_BUDGET`/`DECREASE_BUDGET`) that the guardrail didn't have to cap → auto-applies immediately**, no click. `PAUSE_AD` is never auto-apply eligible (stopping delivery is harder to walk back than a capped budget nudge) and only ever pauses one Ad — a genuine campaign-wide kill switch is now a separate, deliberate mechanism (see "Spend guardrails" below), not part of this recommendation flow.
    - **Everything else (MEDIUM risk, or LOW risk below 90%) → requires approval** — a single explicit **Approve** (applies it to Meta immediately, same "approve = act" shape as "Approve & Publish") or **Reject** action, same UI either way.

    If auto-apply's own Meta call fails (expired token, transient Graph API error), the recommendation falls back to `requiresApproval = true` rather than being silently lost — see `generate_and_store_recommendation`'s except block. The frontend labels an auto-applied recommendation "Applied automatically" (via `requiresApproval === false` + `status === 'APPLIED'`) so it isn't mistaken for something a human clicked.

    - **Manual "evaluate now" only** (`POST/GET .../test-evaluation`, `app/api/test_evaluation.py`) — not yet wired into the scheduled `evaluate_all_live_campaigns` job alongside the recommendation system, a deliberate scoping choice to keep this addition reviewable; automatic scheduling is a natural follow-up, not done now.
    - **The general recommender never fires for a TEST_PLAN campaign** (confirmed 2026-09-01): it assumes exactly one AdSet per campaign, which no longer holds now that "Phase C" (step 5) publishes both audience variants for real — this guard is load-bearing today, not just prospective. Both entry points check the campaign's `plan_type` and refuse rather than guess: the scheduled job's `_evaluate_campaign` (`app/services/optimization_jobs.py`) silently skips TEST_PLAN campaigns before the checkpoint update (they're not this job's business at all — no wasted LLM call, no misleading `lastOptimizationCheckAt` bump), while the manual "Analyze now" endpoint (`POST .../optimize`, `app/api/optimization.py`) returns a visible 400 — `"This is an A/B test — it's evaluated by the test evaluator..."` — routed straight through the frontend's existing `ApiError` → `analyzeErrors` display, so a user who clicks it on a test campaign sees why nothing happened instead of silence.

    **Spend guardrails — manual kill switch, planned end-date enforcement, total-spend circuit breaker (requested and confirmed 2026-09-02, `done`):** three deterministic mechanisms, none of them LLM-gated, addressing the gap the recommendation system's own `PAUSE_AD` (single Ad, always human-approved) deliberately doesn't cover — stopping an entire campaign's spend outright, either on demand or automatically.
    - **Manual pause** (`POST .../campaigns/{id}/pause`, `app/api/campaign.py`) — one click pauses every AdSet in the campaign (`app/services/publish.py`'s `pause_campaign`), not just one Ad; mirrors the local `AdSet`/`Ad` rows to `PAUSED` too, not just Meta. Requires the campaign to be `LIVE`; 400s otherwise (already paused, never published, or Meta disconnected since publishing). Frontend: a "Pause campaign" button next to "Live on Meta," and a "Paused — \<reason\>" line once paused.
    - **Planned end date, enforced two ways:** `publish_campaign_to_meta` now computes an `end_time` and sends it to every AdSet it creates — an event venue's existing `Campaign.endDate` (§5 step 11) wins when set; otherwise a TEST_PLAN gets one computed from its own `duration_days`, starting at publish time (a `DATA_DRIVEN_STRATEGY` with no event venue has no duration concept and gets none, unchanged). Sent as Meta's documented ISO 8601 UTC format — **not yet verified against a real live publish**, same caution as the event-venue geo params above. A scheduled backstop, `pause_expired_campaigns` (hourly, `app/services/optimization_jobs.py`), independently auto-pauses any live campaign whose `endDate` has passed, regardless of plan type — catches a campaign published before this parameter existed, or in case Meta doesn't actually honor `end_time` as documented.
    - **Total-spend circuit breaker** — deterministic, not an LLM judgment call: `_enforce_spend_circuit_breaker` runs right after `collect_metrics_for_all_live_campaigns` (every 15 min) collects each campaign's fresh spend, and auto-pauses a TEST_PLAN whose combined spend across both variants exceeds its own `total_budget` (e.g. $1,000 for the $50/day × 2 variants × 10-day default). Only TEST_PLAN has a fixed total to check against — `DATA_DRIVEN_STRATEGY` is open-ended by design (scaled by its own `scaling_trigger` instead) and is never touched by this breaker, however high its spend climbs.
    - **`Campaign.pausedReason`** (new nullable field) records why, for any of the three paths above — surfaced in `CampaignResponse` and shown in the campaign list, so a paused campaign reads as "Paused — Total spend $1,042.10 exceeded the $1,000.00 planned budget" rather than just "Paused."

    **Three more guardrails, requested and confirmed 2026-09-03, `done`:** a rolling-CAC efficiency circuit breaker (auto-pause), a daily-spend sanity check (flag, not pause), and a default Meta bid cap — the total-spend breaker above catches a campaign that overspent its *plan*, these catch one that's inefficient *right now* or bidding with no cost discipline at all.
    - **Rolling-CAC circuit breaker** (`_enforce_cac_circuit_breaker`, same 15-min cycle as the total-spend breaker) — applies to *either* plan type, unlike the total-spend breaker (TEST_PLAN-only): `target_cac` is a product-level concept, not a TEST_PLAN-specific one. Auto-pauses once the rolling 3-day CAC exceeds 2x target (`_CAC_OVERSPEND_MULTIPLE`), gated on at least $100 of rolling spend (`_MIN_ROLLING_SPEND_FOR_CAC_CHECK`) so a noisy small sample can't trigger it. Real spend with zero purchases over the window is treated as worse than any finite ratio and pauses too, not silently skipped as "can't compute." Computed via a new `Metric.purchases` column (raw purchase count per snapshot, distinct from the broader `conversions` sum and from the lifetime-to-date `cac` ratio, neither of which a rolling window can delta directly) — `spend`/`purchases` deltas between the latest snapshot and the one nearest 3 days ago, summed across every AdSet group (both TEST_PLAN variants, when Phase C applies) for one campaign-wide verdict, reusing `app/services/optimizer.py`'s `nearest_metric_at_or_before`. Target: the campaign's own product economics when available, the jewelry CAC benchmark median otherwise — **never blended**, same principle as `_build_success_criteria`'s benchmark-vs-business-target split.
    - **Daily-spend sanity check** (`_enforce_daily_spend_flag`, same cycle) — monitoring only, never pauses: Meta's own daily-budget pacing can overspend up to ~25% on a given day, evened out across a calendar week (Meta's own documented policy), so a single day over that isn't itself cause to stop a campaign. Checks each real AdSet's own last-24h spend against 1.25x its configured daily budget (`_DAILY_OVERSPEND_MULTIPLE`); sets `Campaign.dailySpendFlag` (new nullable field) with which AdSet(s) and by how much, refreshed every cycle — cleared back to `null` once no longer true, so it never becomes a stuck alert. Frontend: a `⚠` warning line under "Live on Meta" when set.
    - **`Metric.purchases`** (new nullable field, alongside `dailySpendFlag`) — populated from `_fetch_insights`'s already-computed purchase count (`app/services/meta.py`), previously discarded after deriving `cac`/`roas`.
    - **COST_CAP as the default bid strategy** (`create_meta_ad_set`, `app/services/meta.py`) — `bid_strategy` is `COST_CAP` with `bid_amount` set to the same target-CAC-or-benchmark-fallback value the rolling-CAC breaker judges against (resolved once in `publish_campaign_to_meta`, applied uniformly to every AdSet a campaign publishes), replacing the previous unconditional `LOWEST_COST_WITHOUT_CAP`. Complements the deterministic breaker rather than replacing it — Meta doesn't guarantee adherence to a cost cap (its own documented caveat), so the app-side check still matters even with a cap requested. Falls back to `LOWEST_COST_WITHOUT_CAP` only if no target is given at all, which shouldn't happen in practice now that a benchmark fallback always exists. **Not yet verified against a real live publish**, same caution as `end_time`/geo params above.

    **A/B test winner-declaration cycle, requested and confirmed 2026-09-03 — a 5-phase roadmap, Phase 1 `done`, Phases 2-5 planned:** the gap was that `generate_and_store_test_evaluation` only ever ran on a human's manual "Evaluate now" click — a TEST_PLAN could auto-pause (duration elapsed, or either circuit breaker above) and just sit there with no verdict recorded until someone remembered to ask. Variant parity (same creative, budget, `COST_CAP`/target, end date, landing page — only `targeting` differs) was already structurally guaranteed by `publish_campaign_to_meta` computing all of those once and passing them identically into both variants, confirmed by re-reading the code rather than assumed.
    - **Phase 1, deterministic confidence tiers + auto-evaluation wiring (`done`):** `TestEvaluation.confidence` is now backend-computed (`compute_test_confidence`, `app/services/optimizer.py`) from real sample size, never the LLM's own self-assessment (`GeneratedTestEvaluation` no longer has a `confidence` field at all) — `"LOW"` below `MIN_CONVERSIONS_TO_COMPARE_VARIANTS` (3, same floor `compute_test_result` uses to stay `INCONCLUSIVE`), `"DIRECTIONAL"` above that but before both variants clear `MIN_CONVERSIONS_FOR_CONFIDENT_RESULT` (10) conversions *and* `MIN_SPEND_MULTIPLE_OF_TARGET_CAC` (2x) target CAC spent, `"CONFIDENT"` once both gates clear on both sides. `resolve_target_cac` (a new shared helper — the "own economics, benchmark median fallback, never blended" resolution used identically at publish time and by the rolling-CAC breaker) supplies the target. `generate_and_store_test_evaluation` gained a `stop_reason` param and `TestEvaluation.stopReason` (new field, `"MANUAL"` default) records why an evaluation ran — a human's click, or which auto-pause path triggered it (`"TEST_DURATION_ELAPSED"`/`"TOTAL_SPEND_CIRCUIT_BREAKER"`/`"CAC_CIRCUIT_BREAKER"`). `pause_expired_campaigns` and both circuit breakers now call a shared `_auto_evaluate_after_pause` right after pausing a TEST_PLAN campaign (never a DATA_DRIVEN_STRATEGY one, even from the CAC breaker which applies to both plan types) — best-effort: an LLM failure there is logged, not raised, since the campaign is already safely paused either way and a human can still evaluate manually. Frontend shows the new `stopReason` under each evaluation.
    - **Phase 2, planned:** persist past `TestEvaluation` results per business and feed the losing/winning findings into the strategist's prompt, so a new hypothesis doesn't repeat a rejected one — the "running scoreboard" (e.g. "broad audience beats interest-targeted," "video beats static").
    - **Phase 3, planned:** extend TEST_PLAN beyond audience-only to a `test_dimension` (audience → creative → offer), plus campaign lineage so a confirmed winner becomes the next round's baseline.
    - **Phase 4, planned, confirmed 2026-09-03 it must never be automatic:** promoting a winner into a new "scaling" campaign (winning ad set's settings, roughly the same daily budget) and drafting the next test cycle always requires one human click to actually go live — the system may draft, never auto-launch a new paid campaign.
    - **Phase 5, planned:** a winner-decay monitoring job — when a promoted winner's performance drops, rotate in the next creative winner.
11. **Event/venue geo-targeting** — lets a business target ads at people near a specific major US jewelry trade show venue (e.g. JCK Las Vegas, Couture at Wynn, AGTA GemFair Tucson, JA New York at the Javits Center) instead of only broad city/region/country targeting. Requested and confirmed 2026-09-01. *(done)*

    **Curated, not live-resolved** — same "backend decides structural facts" reasoning as the interest lookup table built for "Phase C" (step 5), but simpler: major annual jewelry trade shows are a small, fixed, well-known set, and venue coordinates don't churn the way Meta's interest taxonomy does, so this needed no live API call and no freshness/re-validation job. A static table, `app/services/event_venues.py`:
    ```
    EventVenue = {key, name, venue, city, state, lat, lng, typical_month, typical_duration_days, recommended_radius_miles}
    ```
    Seeded with four well-known recurring shows to start (JCK Las Vegas, Couture, AGTA GemFair Tucson, JA New York) — hand-curated, never LLM-sourced; more can be added the same way. `default_event_window(venue)` computes a venue's next typical occurrence (the 1st of `typical_month` through `typical_duration_days` later, rolling to next year once that month has passed) as a deliberately simple default, never an authoritative calendar.

    **Meta mechanics:** targets via `custom_locations` (a center point + radius) instead of `geo_locations.countries` — a different AdSet targeting shape than the previous default (still hardcoded to `{"countries": ["US"]}` for a non-event campaign, age-range only — PRD.md §5 step 8's "known simplifications" note, otherwise unchanged). `create_meta_ad_set` (`app/services/meta.py`) takes an optional `custom_location: CustomLocation` (`{lat, lng, radius_miles}`) that, when given, entirely replaces the country-list geo — Meta doesn't mix the two within one targeting spec. `radius_miles` is sent as `distance_unit: "mile"` as-is; **not yet verified against the real Graph API** (same "real end-to-end testing catches what mocks can't" caution as the rest of this function's real-API-confirmed fixes) — flag if a live publish rejects the radius bounds/unit.

    **Campaign fields, plan-type agnostic:** `Campaign.eventVenueKey`/`startDate`/`endDate` (all nullable) — set at campaign creation (`POST .../campaigns`), not part of the Strategist's LLM-generated content at all (event choice is a user/business call, same "backend/user decides structural facts, LLM never invents them" reasoning already applied to `objective`/`plan_type`). `eventVenueKey` must resolve against the curated table (404 `"Unknown event venue"` otherwise, same "not found" treatment as an unresolvable product/audience id). `startDate`/`endDate` default from `default_event_window` when omitted alongside an `eventVenueKey`, always overridable by explicit dates in the request. `publish_campaign_to_meta` (`app/services/publish.py`) resolves the campaign's venue (if any) into a `CustomLocation` independent of `strategy.plan_type` — applied uniformly to every AdSet a campaign publishes, including both of a TEST_PLAN's variants now that "Phase C" (step 5) is built. This event venue's geo constraint stays the same for both variants (it's a fact about the campaign — "people near this venue" — not something either variant individually decides); the "Variant B becomes the event audience" idea floated in this step's original draft never had anything to attach to structurally, since location was never part of what distinguishes the two variants from each other in the first place.

    **Frontend:** `CampaignsSection`'s create-campaign form gets an "Event venue" dropdown (`None — broad US targeting` plus the curated list, mirrored as a small static `EVENT_VENUES` constant in `frontend/src/lib/api.ts` — same "small, fixed, no endpoint needed" reasoning already used for the `Objective` union) and, once a venue is picked, optional start/end date inputs with a hint that blank dates default from the venue. A live campaign with an event venue set shows it (plus its window) on the campaign list.

    **Explicitly deferred:** multiple concurrent event campaigns, an event calendar/reminder feature ("your event is coming up, want to launch?"), non-jewelry event types, events outside the US, and any Strategist LLM-prompt awareness of the chosen event (hypothesis/creative-angle copy doesn't yet reference "near this venue" — a natural follow-up, not required for the geo-targeting mechanic itself to work).
