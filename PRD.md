# Sales Guru — Product Requirements Document

## 1. Summary

Sales Guru is an AI-powered advertising platform for small-to-medium businesses: a user links their business, describes what they sell, and the platform generates ad strategy, ad copy, and ad creative using AI — then publishes real campaigns to Meta Ads and reports back on results.

Functional reference for scope/pricing: saleads.ai/es/subscribe. Sales Guru is an independent product — own name, brand, and copy, not a reskin.

**Vertical scope (confirmed 2026-08-31):** MVP is scoped to the jewelry & accessories industry only, not general-purpose across industries. The Marketing Strategist Agent (§5 step 5) is grounded with jewelry-specific knowledge and validated industry benchmarks for this vertical rather than staying industry-agnostic.

## 2. MVP core loop

The MVP is this end-to-end flow, in order. Each step is a fully working component before moving to the next (see §5, Build order).

1. **Create account** — sign up / log in
2. **Create business** — business profile (see §7 for exact fields)
3. **Describe product & define audience** — what the business sells, and who buys it (see §7 for exact fields)
4. **Upload images** — product/brand image assets, used as ad creative input
5. **Select objective** — campaign goal (see §7 for the exact value set — maps to Meta Ads campaign objectives)
6. **Connect Meta Ads** — OAuth into the user's Meta Business account, select ad account + Page
7. **AI generates strategy** — targeting, budget, objective-specific recommendations grounded in the business profile + product description
8. **AI generates ads** — ad copy variants + ad creative (composed from uploaded images and/or AI-generated), grounded in the strategy
9. **User approves** — review the generated strategy + ads; a single explicit **"Approve & Publish"** action is the only thing that triggers step 10 — approving never silently publishes on its own (see the checkpoint note under §5 step 8)
10. **Campaign goes live** — publish via the Meta Marketing API (create campaign / ad set / ad)
11. **Dashboard shows results** — pull performance metrics back from the Meta Ads Insights API

**Assumption (flag if wrong):** billing/subscriptions and credit metering are *not* part of this MVP loop — the priority is proving the core value loop (account → live campaign → results) before monetization. Billing moves to post-MVP (§4). The plan/pricing table in §3 is the target monetization model once billing is built, not an MVP requirement.

## 4. Out of scope for MVP (explicitly deferred)

- **Billing/subscriptions/credits** — no payment gate in MVP; all AI generation is unmetered until billing lands post-MVP
- **Google Ads / TikTok Ads publishing** — Meta Ads only for MVP; other platforms require separate API integrations, deferred
- **Agency tier / multi-client management**
- **Team seats / multi-user per business**

**Known external dependency / risk:** Meta Marketing API access requires Meta App Review and Business Verification before the app can create live campaigns on a user's behalf beyond a small set of test users. This is an external approval process outside our control — build the integration against Meta's sandbox/test mode first, and treat App Review as a launch blocker to track separately, not an engineering task we can shortcut.

**Resolved (2026-09-01):** the session cookie now switches to `samesite=none; secure` in production (`app/api/auth.py`'s `_cookie_cross_site_attrs()`), covering the cross-site relationship between the separate Render frontend/backend subdomains; dev keeps `samesite=lax` with no `secure` flag since localhost frontend/backend share an origin. `render.yaml` now also sets `FRONTEND_URL`/`BACKEND_URL`/`CORS_ORIGINS` (backend) and `VITE_API_URL` (frontend) to Render's default `<service-name>.onrender.com` hostnames — `CORS_ORIGINS` in particular is required alongside the cookie change, since a credentialed cross-site request is blocked by CORS before the cookie's `SameSite` attribute is ever consulted. If either service ends up on a different hostname than Render's default pattern, these four values need to be updated to match.

**Resolved (2026-09-02):** the first real Render deploy attempt failed — `schema.prisma`'s `datasource` was still hardcoded to `provider = "sqlite"`, which rejects a Postgres `DATABASE_URL` outright. This had been carried as an implicit to-do since §6/§1's "SQLite dev → Postgres prod" line was written, never actually executed. Fixed with a second, mirrored schema file, `backend/prisma/postgres/schema.prisma` (`provider = "postgresql"`, otherwise identical models) with its own migration history — Prisma migration SQL is dialect-specific, so a single schema.prisma can't serve both providers; `render.yaml`'s build now points `prisma generate`/`migrate deploy` at the Postgres file via `--schema`. See README.md's Database schema changes section for the process to keep both schemas in sync going forward.

Two further issues surfaced getting that first real deploy live, both resolved 2026-09-02:
- **Region mismatch:** the free-tier Render Postgres instance (`sales-guru-db`, 30-day expiry, expires 2026-10-01 unless upgraded) landed in Ohio while the web services are in Oregon — Render's private network doesn't span regions, so the backend couldn't reach the DB's Internal Database URL (`P1001: Can't reach database server`). Fixed by pointing `DATABASE_URL` at the database's *External* Database URL instead (works over the public internet regardless of region). Worth revisiting later — recreate the DB in Oregon and switch back to the Internal URL for lower latency and no public egress, once there's real data worth the migration.
- **Missing query engine binary at runtime:** the build succeeded (migrations applied cleanly) but the app crashed on startup with `prisma.engine.errors.BinaryNotFoundError` — `prisma-client-py`'s default binary cache lives under the build user's home directory (`~/.cache/prisma-python`), which is outside the project directory Render actually ships to the running instance, so the query engine binary downloaded at build time wasn't there at boot. Fixed by setting `PRISMA_BINARY_CACHE_DIR=.prisma-cache` (project-relative) in `render.yaml`.

Once live, manual click-through testing against the real production deploy (2026-09-02: signup, business/product/audience creation all verified working end-to-end against the real Postgres DB) surfaced one more deploy-config bug, also resolved 2026-09-02:
- **Deep links 404 on the static frontend:** `App.tsx` uses react-router's `BrowserRouter` (real History API routes), but Render's static site serves files directly — hitting a route like `/businesses/:id` via a hard refresh or a shared link 404s, since no such file exists on disk (only `/index.html` does). Fixed with a Render static-site rewrite rule in `render.yaml` (`source: /*` → `destination: /index.html`) so every path falls through to the SPA shell and React Router takes over client-side.

**Resolved (2026-09-02):** `MetaConnection.accessToken` (build step 6) is now encrypted at rest — unlike `User.hashedPassword`/`Session.tokenHash`, this token has to be usable later for real Marketing API calls, not just verified, so it can't be a one-way hash. Uses Fernet symmetric encryption (`cryptography` package, new dependency) via `app/core/crypto.py`, keyed by a new `META_TOKEN_ENCRYPTION_KEY` env var. Every read site was routed through a single shared, decrypting fetch — `app/core/meta_connection.py`'s `get_meta_connection()` — instead of calling `db.metaconnection.find_unique` directly, so `connection.accessToken` stays a plain string everywhere it's already used downstream (`publish.py`, `optimization_jobs.py`, `strategy.py`, `metric.py`, `campaign.py`); only that one fetch helper and the single OAuth-callback write site (`app/api/meta.py`) needed to change.

## 5. Build order (one component at a time, each fully working before the next)

1. **Foundation** — React 19 + TS + Vite frontend, Python (uv) + FastAPI backend, Prisma schema (SQLite dev → Postgres prod) via `prisma-client-py`, test/lint/CI tooling. *(done)*
2. **Auth** — `POST /auth/signup` (auto-provisions Organization, auto-logs in), `/login`, `/logout`, `/me`; DB-backed sessions via httpOnly cookie, tokens hashed at rest. Frontend: `/login`, `/signup` pages, `AuthProvider`/`useAuth`, route guards. *(done)*
3. **Business + product + audience onboarding** — Business (dashboard: list + create form), Product, and Audience (both on a `/businesses/:id` detail page, via `ProductsSection`/`AudiencesSection`) all done, backend + frontend. `GET /businesses/{id}` added for the detail page.

   **Product image upload, closing this step (confirmed 2026-09-02, `done`):** real photo uploads only — AI-generated images are explicitly deferred to a later pass (the Creative Agent already produces an `imagePrompt` per variant, so that hook exists whenever it's picked up). **Storage: Option A, image bytes in the database** (`ProductImage.data: Bytes` + `contentType`, confirmed 2026-09-02) — no object storage account/credentials needed at MVP scale, survives Render's ephemeral filesystem since Postgres persists, and the app's existing "no new infrastructure" precedent (APScheduler over Redis/Celery, step 10) already established this bias. `POST/GET/DELETE .../products/{id}/images` (`app/api/product_image.py`) are session-authed and ownership-scoped like everything else; jpeg/png/webp only, 5MB cap.
   - **A public, unauthenticated serving route is unavoidable and deliberate:** `GET /product-images/{id}` has no `get_owned_business` check — same split as `app/api/meta.py`'s `router`/`callback_router` (the Meta OAuth callback is hit directly by Meta, not through the frontend). Meta's own servers fetch the ad creative image URL directly for `link_data.picture` (`app/services/meta.py`), not through the browser with the user's session cookie, so this route genuinely can't be behind the normal auth dependency. The id in the URL is an unguessable cuid, not a sequential index, and product images are meant to be shown to the public in ads anyway, so there's no meaningful confidentiality loss.
   - **New `BACKEND_URL` setting** (`app/core/config.py`, mirroring the existing `FRONTEND_URL`) builds the absolute, publicly-fetchable image URL — a relative path won't do, since Meta's servers (not the browser) fetch it. Defaults to `http://localhost:8000` in dev, which Meta genuinely cannot reach — image-backed ad creatives only really work once deployed. **Set in `render.yaml` as of 2026-09-01** (see §4's cookie/CORS resolution note above) to Render's default `<service-name>.onrender.com` hostname.
   - **Wired into creative selection, not publish:** `POST .../creatives/{id}/select` (`app/api/creative.py`) auto-attaches the campaign's product's oldest uploaded photo as `Creative.imageUrl` when one exists and the creative doesn't already have one — the natural checkpoint moment before publish, and the point where the frontend can show the user what image the ad will actually use (`imageUrl` is now exposed on `CreativeResponse`, previously absent). `app/services/publish.py` already passed `creative.imageUrl` through to `create_meta_ad_creative` unconditionally — that plumbing existed since step 8 but had nothing to send until now.
   - **Not yet verified against a real live publish:** Meta actually fetching our served URL for `link_data.picture` — same "flag it, don't assume" caution already applied to the event-venue radius and the geo-taxonomy cities/regions shape.
4. **Objective + Meta Ads connection** — objective selector done: `POST/GET /businesses/{id}/campaigns` (`CampaignsSection`), objective is one of the fixed PRD.md §7 values, campaign optionally references a product/audience from the same business (cross-business references 404, scoped lookup). *(done)*
5. **AI strategy generation** — LLM call grounded in business/product/objective, stored strategy record *(done)*

   **Two-mode agent (confirmed 2026-08-31):** the Strategist Agent (`app/services/strategist.py`) generates one of two distinct plan shapes, decided by the backend (never the LLM), same "backend decides, agent never invents it" reasoning as `Campaign.objective` being fixed input: **TEST_PLAN** for a business with no meaningful advertising history, **DATA_DRIVEN_STRATEGY** for one with real historical performance (a full strategy plus `keyLearnings`/`recommendedAdjustments`/`scalingTrigger` — distinct from the live Optimization Agent, step 10 below, which reacts to *this* campaign's own live metrics rather than *other* past campaigns).

   **plan_type decision (`app/api/strategy.py`), in priority order:**
   1. **Real Meta ad-account history wins over everything** — once a business connects Meta Ads (step 6), `fetch_account_historical_performance` (`app/services/meta.py`) pulls lifetime per-campaign insights for the *whole ad account* (not just campaigns Sales Guru itself published — catches a business that advertised on Meta before ever using this product). Any nonzero spend at all (`has_meaningful_history`, no dollar threshold) means DATA_DRIVEN_STRATEGY, grounded in those real numbers.
   2. **Otherwise, a one-time self-reported answer** — `Business.hasPriorAdvertisingExperience`, asked once (in the Strategy-generation UI, "Has this business run marketing/ad campaigns before?") and stored permanently once answered; never asked again for that business. Real Meta history, if it later appears, still overrides even a stored "no" — self-report never wins over evidence.
   3. **Neither available yet** — the endpoint returns `428 Precondition Required`, and the frontend must prompt for the one-time answer and resubmit it in the request body (`CreateStrategyRequest.hasPriorAdvertisingExperience`).

   **TEST_PLAN is a structured advertising experiment, not just two recommended audiences (confirmed 2026-09-01, "Phase A" of a larger redesign — Phase B, an Optimizer that consumes this plan against real results, `done`; Phase C, real two-adset Meta publishing plus real Meta interest targeting, `done`, confirmed 2026-09-02 — see the "Phase C" bullets below):**
   - **Two audience variants, always.** **Variant A (`broad_baseline`)** is entirely backend-constructed — deliberately empty/unconstrained targeting (Meta's Advantage+-style automated delivery, where the objective supports it), no invented interests, the experiment's control. **Variant B (`hypothesis_audience`)** is the only thing the LLM designs: one specific, non-interest-stacked audience grounded in the real product/business/audience data — simple enough to interpret, specific enough to test a real hypothesis. `app/schemas/strategy.py`'s `AudienceVariant`/`GeneratedTestPlanFields` encode exactly which sub-fields are backend-fixed vs. LLM-generated.
   - **One primary hypothesis, falsifiable.** `hypotheses: [TestHypothesis]` — `baseline_variant`/`test_variant`/`primary_metric` (`cac`)/`secondary_metrics` (`ctr`, `cpc`, `add_to_cart_rate`, `conversion_rate`, `roas`) are backend-fixed (every TEST_PLAN compares the same two variants the same way); only the LLM-generated `statement` text varies, so it can name the actual audience specifics rather than reading as a template sentence. The purpose is to collect evidence, not assume a winner — Sales Guru never claims to know the answer before the experiment runs.
   - **Budget/duration are a backend business rule, not an LLM recommendation or an absolute advertising truth** (confirmed 2026-09-01): `_compute_test_daily_budget` (`app/services/strategist.py`) uses `DEFAULT_TEST_BUDGET` ($50/day) and `DEFAULT_TEST_DURATION` (10 days) when the product has no computable unit economics; otherwise the daily budget is anchored to the product's own `target_cac` (a productive test should buy roughly one conversion a day at that rate), clamped to `[MIN_TEST_BUDGET, MAX_STARTING_BUDGET]` = `[$20, $75]`/day (constants in `app/schemas/strategy.py`). The LLM is told the resulting numbers as context, never asked to set them. `dailyBudget` is a **per-variant** rate — each of the TEST_PLAN's two `audienceVariants` gets its own AdSet spending at this rate, so actual total daily spend is `dailyBudget × 2` (confirmed 2026-09-01). `totalBudget` is backend-computed as `dailyBudget × audienceVariants.length × durationDays` (e.g. $50/day × 2 variants × 10 days = $1,000, not $500).
   - **`success_criteria` splits leading indicators (CTR, CPM, add-to-cart rate — a useful read with little data) from economic indicators (conversion rate, CAC, ROAS — need more volume)** — a cold-start test shouldn't define success exclusively as "hit target ROAS." Every criterion carries a `direction` (`higher_is_better`/`lower_is_better`, from `benchmarks.py`'s `METRIC_DIRECTIONS`) so "better" is always known even for metrics with no numeric benchmark yet (CPC, ROAS, add-to-cart rate).
   - **`benchmark` (industry-wide) and `business_target` (this specific business's own economics) are two separate numbers on every criterion, never blended into one** (confirmed 2026-09-01) — a $2,000 product at 50% margin needing "CAC below $100" is a business target that has nothing to do with what the broader jewelry industry typically sees; an earlier draft of this design picked "whichever is more conservative" between the two, which silently hides one fact behind the other. `benchmark_context` (the industry side) and `unit_economics` (the business side, below) stay as separate top-level fields on the plan for the same reason.
   - **`decision_rules`** — fixed `{condition, action}` pairs (e.g. `"hypothesis_audience has lower CAC with sufficient conversion volume" → "prefer_hypothesis"`) comparing the two named variants, telling a future Optimizer what to do with the result; never LLM-generated, so they stay consistent across every test plan and machine-matchable on `action`.
   - **`baseline_metrics`** — the full normalized metric shape (`impressions`/`reach`/`spend`/`cpm`/`clicks`/`ctr`/`cpc`/`landing_page_views`/`add_to_cart`/`add_to_cart_rate`/`conversions`/`conversion_rate`/`cac`/`purchase_value`/`roas`), all `null` at plan-generation time — `null` means unavailable/not-yet-collected, never zero. This is the shape real Meta metrics will eventually populate (Phase B); not every campaign objective produces every metric.
   - **`data_source`** — explicit provenance tagging which fields came from business facts, historical Meta data (always empty for TEST_PLAN — that's what routes a business to DATA_DRIVEN_STRATEGY instead), industry benchmarks, or AI-generated content, per the product requirement to never present a benchmark estimate as actual business performance.
   - **"Phase C" real two-variant Meta publishing (confirmed 2026-09-02, `done`):** a TEST_PLAN campaign now publishes both `audience_variants` as real, independent AdSets/Ads on Meta — `primary_audience()` (still used by DATA_DRIVEN_STRATEGY's single-AdSet path) is no longer the TEST_PLAN publish path. `app/services/publish.py`'s `publish_campaign_to_meta` branches on `strategy.plan_type`: the broad baseline gets `targeting_automation.advantage_audience=1` (Meta-driven delivery, deliberately no interests, per this variant's own design above) and the hypothesis-driven variant gets `advantage_audience=0` with its real resolved interests (see the interest-resolution bullet below); both get the *same* per-variant `dailyBudget` rate and the *same* geo target (an event venue's radius, PRD.md step 11, when the campaign has one — the geo constraint is a fact about the campaign, not about either variant individually). One Meta ad creative object is created and reused across both `create_meta_ad` calls; locally, `Creative.adId` is a single nullable FK (one Creative row → at most one Ad), so the originally SELECTED row is linked to the baseline's Ad and a duplicate row (same content, same `metaCreativeId`) is created for the hypothesis variant's Ad — Meta only ever sees one creative object, the duplication is purely a local-data-model consequence.
   - **Interest resolution (confirmed 2026-09-02, `done`, part of "Phase C"):** `TargetAudience.interests` is no longer free text — it's constrained to a dynamically-built `Literal` enum of curated keys (`InterestKey`, `app/schemas/strategy.py`) sourced from `app/services/interests.py`'s `INTERESTS` table, so forced tool-use plus this enum means the Strategist LLM can never emit an interest that doesn't resolve to a real Meta interest id. The curated table (39 entries as of this writing) was built by hand-picking real, currently-valid results from Meta's real Targeting Search endpoint (`GET /search?type=adinterest`, confirmed live against a real ad account 2026-09-02) across ~20 jewelry-related seed terms, via the re-runnable `scripts/resolve_interests.py discover` (prints candidates for review — curation is a relevance judgment call, deliberately not automated) and `validate` (re-checks the curated table's ids against `GET /search?type=adinterestvalid&interest_fbid_list=[...]` — note `interest_fbid_list`, not the more obvious `interest_list`, which silently returns `valid=false` for every id regardless of correctness, a real API quirk only caught by testing against the live endpoint) subcommands. Each entry stores its own `resolved_at`, same per-entry freshness pattern as `benchmarks.py`'s `as_of` — re-run `validate` periodically, since Meta periodically deprecates detailed-targeting options. Publish-time resolution (`app/services/publish.py`'s `_resolve_interests`) is a plain dict lookup, no fuzzy matching, no runtime API dependency — applies to both TEST_PLAN's hypothesis variant and DATA_DRIVEN_STRATEGY's `target_audience` (interests reach Meta's real targeting spec for the first time via this change; previously not sent at all, see step 8's "known simplifications" note).
   - **Explicitly attempted and abandoned: pre-create `targetingvalidation` check.** The plan going into "Phase C" was to call Meta's `GET /act_{id}/targetingvalidation?targeting_list=[...]` before `create_meta_ad_set`, so a stale/dead interest id (or malformed targeting spec) fails loud at validation instead of mid-publish. Tested for real against a live ad account 2026-09-02: this endpoint returns `{"valid": false}` even for a targeting spec that had *just* been used to successfully publish a real live AdSet — with no error/reason field to explain why, and no combination of extra params (`optimization_goal`, `objective`, `fields=valid,errors,warnings`) changed the result. Wiring this in as designed would have incorrectly blocked every real publish, so it was not built — flagged here rather than silently dropped, in case Meta's real behavior here is later understood well enough to revisit.
   - **Geo-taxonomy resolution (confirmed 2026-09-02, `done`):** `TargetAudience.location` is no longer free text — it's `list[TargetLocation]` (`{city, region}`, `app/schemas/strategy.py`), resolved live at publish time against Meta's real Geo Search endpoint (`GET /search?type=adgeolocation`, `app/services/meta.py`'s `search_ad_geolocations`; `app/services/geo.py`'s `resolve_target_location`). Locations aren't a fixed small vocabulary like interests, so this can't be pre-curated the same way — it resolves live, not from a static table. The "Springfield problem" this exists to reduce is real, not theoretical: confirmed live against the API 2026-09-02, searching "Springfield" alone returns 25+ candidates across a dozen-plus US states (plus Australia and the UK) with no single obviously-right answer. Resolution: filter to `country_code == "US"` (this MVP is US-only everywhere already — `BenchmarkContext.country`, the default `geo_locations.countries` — so this is a backend constraint, never a per-business lookup or something the LLM picks); if a `region` hint is given and narrows the US candidates to exactly one, use it (high confidence); otherwise fall back to Meta's own top-ranked result and log a low-confidence warning rather than fail — a location that resolves ambiguously is still better than one that blocks the whole publish. A location with genuinely zero US matches raises `GeoResolutionError` (a `MetaConnectionError` subclass, so it flows through the exact same `except MetaConnectionError` → `FAILED`/retryable handling as any other Graph API failure, no parallel error path needed). At publish time, a resolved city/region entirely replaces the default `{"countries": ["US"]}` geo the same way an event venue's `custom_locations` already does (`create_meta_ad_set`'s `resolved_locations` param, `app/services/meta.py`) — and is skipped entirely when the campaign has an event venue, same "the event's geo constraint applies uniformly, not per-variant" precedence as `custom_location`. Applies to both TEST_PLAN's hypothesis variant and DATA_DRIVEN_STRATEGY's `target_audience`. **Not yet verified against a real live publish:** the exact `geo_locations.cities`/`.regions` request shape (`{"key": ...}` per entry, no radius) is built from documentation-level confidence, not a confirmed real Graph API call — flag if a live publish rejects it, same caution already noted for the event-venue `custom_locations` radius/units.
   - **Still unverified, not part of this pass:** the new AdSet targeting shape (advantage_audience=1 for a baseline paired with real interests/locations on the other variant, all under one campaign) hasn't itself been exercised in a real live publish yet — the individual pieces (interest search/validate, geo search, the existing single-AdSet publish mechanics this reuses) have each been confirmed against the real API separately, but not this exact combination end-to-end, since doing so means real ad spend on a real ad account and needs the user's own call on when to run it.

   **Jewelry & accessories industry benchmarks are ranges with metadata, not single points (confirmed 2026-09-01, `app/services/benchmarks.py`)** — a single number invites false precision downstream ("your CTR of 2.38% failed the 2.42% threshold" is noise, not signal, when the source is one validated median):
   ```
   BenchmarkRange = {low, median, high, source, as_of, direction}
   ```
   `classify_performance_zone(value, benchmark)` maps a value to one of four zones — `needs_attention` (worst) → `within_acceptable_range` → `strong` → `exceptional` (best) — resolved by `direction` so this reads correctly for both higher-is-better metrics (CTR, CVR, ROAS) and lower-is-better ones (CPM, CAC, CPC); not yet wired into anything live (that's the Optimizer, Phase B). Current Meta/jewelry ranges, user-validated median with an estimated ±20% band (no independently-sourced percentile data exists yet — revisit if real percentile benchmarks become available):
   - CTR: 1.94%–2.90% (median 2.42%, higher is better)
   - CPM: $7.49–$11.23 (median $9.36, lower is better)
   - Conversion rate: 0.68%–1.02% (median 0.85%, higher is better)
   - CAC: $36.40–$54.60 (median **$45.50**, lower is better)

   Google Ads figures (sourced from wordstream.com) stay flat points, not ranges — informational grounding only, never acted on or measured against, since this product only publishes to Meta: CTR 6.64%, CPC $4.44, conversion rate 4.50%, cost per lead $97.51.

   **Unit economics (confirmed 2026-08-31, extended 2026-09-01 with `breakeven_roas`; `app/services/unit_economics.py`):** when the campaign's product has both `price` and a nonzero `margin` set,
   ```
   gross_profit = price * margin        # margin is a fraction, e.g. 0.4 for 40%
   breakeven_cac = gross_profit
   target_cac = gross_profit * 0.33
   breakeven_roas = 1 / margin          # price cancels out
   ```
   These are this business's own profitability facts ("business economics"), kept structurally separate from the industry benchmark ranges above ("industry benchmark") everywhere they appear on a TEST_PLAN — never blended into a single number (see the `success_criteria` bullet above). Falls back to no business-specific target (industry benchmarks only) when price/margin aren't set. **Known unit ambiguity, not yet resolved:** `Product.margin`'s exact unit was already flagged unconfirmed elsewhere in this doc (§7) — this formula assumes a fraction (0.4), not a whole percentage (40); revisit both together if that assumption is wrong.
6. **AI ad generation** — ad copy + creative generation grounded in the strategy *(done)*. Also where the Meta Ads OAuth connection itself lives (`app/api/meta.py`, `MetaConnectionSection`): connect → pick ad account + Page → `MetaConnection` stored, scoped per business. Built as its own component ahead of schedule (originally deferred to step 8 per an earlier version of §6) — actual campaign publishing (create campaign/ad set/ad on Meta) is still step 8, separate from this connection step.
7. **Approval flow** — review/edit UI, explicit user approval gate before publish *(done)*
8. **Campaign publish** — Meta Marketing API integration to create live campaign/ad set/ad from approved content, using the ad account/Page selected in step 6. *(done)* `POST .../campaigns/{id}/publish` (`app/services/publish.py`) creates Campaign → AdSet → AdCreative → Ad on Meta in sequence, mirrors them locally (first-ever `AdSet`/`Ad` rows), and moves `Campaign.status` to `LIVE` (or `FAILED`, retryable). Frontend's single **"Approve & Publish"** button calls approve (if still `PENDING_APPROVAL`) then publish in one user-triggered flow, satisfying the checkpoint requirement below without ever auto-publishing on its own.
   **Checkpoint requirement (confirmed 2026-08-08):** AI creates campaign → user reviews → single explicit "Approve & Publish" action → Meta API call — done, see above. 10. **Campaign optimization agent** — AI recommends pausing an underperforming ad, increasing budget on a well-performing one, or decreasing budget on a struggling one, grounded in the campaign's `Metric` history; a LOW-risk, high-confidence budget nudge can apply itself, everything else waits for an explicit checkpoint. Was out of scope for MVP (§4, old revision) until real performance data started flowing in step 9 — now buildable. *(done)*

    **Architecture (confirmed 2026-08-09):** two APScheduler jobs, in-process, no new infrastructure (no Redis/Celery/external cron — same Prisma/SQLite-dev/Postgres-prod DB as everything else, not a separate store):
    - `collect_metrics_for_all_live_campaigns` (every 15 min) — pure metrics collection for every live, Meta-connected campaign, no decisions made. Same Insights pull as step 9's manual "Refresh results," just scheduled.
    - `evaluate_all_live_campaigns` (every 60 min) — gate-checks each live campaign against **Event + Time + Data Sufficiency** (`has_sufficient_data`: hours since last check ≥6h AND spend since last check ≥$20 AND clicks since last check ≥30, all three ANDed) before spending an LLM call, so a campaign isn't re-analyzed off a normal fluctuation or before it has enough signal. This collapses the originally-discussed separate "4-6h lightweight check" and "24h deep optimization" tiers into one job with an internal ~24h-per-campaign cadence (`MIN_HOURS_BETWEEN_RECOMMENDATIONS`), rather than building a second, under-specified lightweight-analysis pathway — a scoped simplification of the reference 3-tier design, not the full spec.

    Once the gate passes, the agent computes real trend windows (24h/3d/7d deltas, via `compute_trend_windows`/`nearest_metric_at_or_before` diffing the latest cumulative `Metric` snapshot against the closest prior one) rather than reasoning over Meta's raw lifetime-to-date numbers — comparing recent performance against a spread of history is what prevents "CTR dipped this morning → PAUSE" reactions to noise. The LLM (forced tool-use, same pattern as Strategist/Creative) returns a structured recommendation — `action_type`, `reasoning`, `confidence` (0-1, self-assessed), `risk` (LOW/MEDIUM/HIGH, self-assessed), `suggested_budget` (optional) — never a single accept/reject question. Any budget suggestion is capped by a backend guardrail (`apply_budget_guardrail`, max ±20% change) before it's ever stored, never trusted raw from the LLM.

    `app/services/optimizer.py` is the pure agent (gate logic, trend computation, the LLM call, guardrail) with no DB access; `app/services/optimization_jobs.py` is the DB-touching orchestration layer the scheduler (`app/core/scheduler.py`) and the manual "generate now" endpoint both call — same pure-service-vs-orchestration split already used for publish (`app/services/meta.py` vs. `app/services/publish.py`). `apply_recommendation` (in `optimization_jobs.py`) is the single place that actually calls Meta for a recommendation, shared by the manual Approve click and the auto-apply path below.

    **Checkpoint requirement (confirmed 2026-08-08, tiered 2026-08-09):** `requiresApproval` is computed by the backend (`compute_requires_approval`), never taken from the model. Risk is a hard gate, not something confidence can override:
    - **HIGH risk → always a mandatory checkpoint**, regardless of confidence (e.g. a $50/day → $500/day jump stays mandatory even at high confidence).
    - **LOW risk + confidence ≥ 90% (`AUTO_APPLY_CONFIDENCE_THRESHOLD`), on a budget action (`INCREASE_BUDGET`/`DECREASE_BUDGET`) that the guardrail didn't have to cap → auto-applies immediately**, no click. `PAUSE_AD` is never auto-apply eligible (stopping delivery is harder to walk back than a capped budget nudge) and no per-business/per-campaign opt-out exists yet (confirmed with the user: budget actions only, no kill switch for now).
    - **Everything else (MEDIUM risk, or LOW risk below 90%) → requires approval** — a single explicit **Approve** (applies it to Meta immediately, same "approve = act" shape as "Approve & Publish") or **Reject** action, same UI either way.

    If auto-apply's own Meta call fails (expired token, transient Graph API error), the recommendation falls back to `requiresApproval = true` rather than being silently lost — see `generate_and_store_recommendation`'s except block. The frontend labels an auto-applied recommendation "Applied automatically" (via `requiresApproval === false` + `status === 'APPLIED'`) so it isn't mistaken for something a human clicked.

    **TEST_PLAN evaluation, "Phase B" of the test-plan redesign (confirmed 2026-09-01, `done`):** a second, distinct evaluation path answering "did the campaign accomplish what the Test Plan set out to test?" — separate from the recommendation logic above, which applies regardless of plan type.

    - **`winningVariant`/`hypothesisResult` are now real, not permanently `null`/`"INCONCLUSIVE"` (confirmed 2026-09-02, `done`):** once both variants have their own per-AdSet `Metric` history, `has_sufficient_test_data_for_variants` (`app/services/optimizer.py`) gates on each variant individually clearing its own fair-share budget (`dailyBudget × durationDays` — a variant's full planned spend, since `dailyBudget` is already per-variant) *or* the shared test duration elapsing — a lopsided spend split (one variant funded, the other barely touched) isn't treated as sufficient even if the combined total looks ready.     - **Extended `Metric` fields** (all nullable, `null` = unavailable, never zero): `reach`, `cpm`, `ctr`, `cpc`, `landingPageViews`, `addToCart`, `addToCartRate`, `conversionRate`, `cac`, `purchaseValue`, `roas` — populated by an extended `fetch_campaign_insights`/`fetch_ad_set_insights` (`app/services/meta.py`, sharing one `_fetch_insights` implementation since Meta's Insights API is symmetric across Campaign/AdSet object levels) pulling Meta's `actions`/`action_values` breakdown. `cac`/`roas` are computed from purchase-specific action types only (`purchase`, `omni_purchase`, `offsite_conversion.fb_pixel_purchase`), not the broader `conversions` figure, since mixing in link-clicks/leads would be misleading.
